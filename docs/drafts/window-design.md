## 1. 设计定位与核心原则

本监控器是研究人员在 Windows 桌面端长期常驻挂载的“深度学习训练只读仪表盘”。其核心任务是**在不干扰远端或本机训练进程的前提下，真实、清晰、可信地反映训练进度、检查点落盘与健康状况**。

根据 `docs/requirements-and-evidence.md` 的既定约束、`docs/reviews/design-alignment.md` 主控核对意见与前端工业工具设计规范，确立以下核心原则：

1. **绝对证据导向（Evidence-First），杜绝推测式 UI**：
   - 界面上每一处状态指示必须有明确的只读证据链支撑（进程实例、文件身份、已提交 offset、状态 JSON、只读解析结果）。
   - 证据缺失或冲突时显示“待确认（Unconfirmed）”与证据卡，不擅自推测训练“成功”或“崩溃”。
   - 检查点文件在磁盘存在**仅表示发现文件元数据（file_found）或只读元数据（metadata_read）**，在未进行安全权重恢复测试前，严禁标为“保存成功”或“已验证可恢复”（首版明确不加载大体积模型权重）。
2. **连接状态与任务生命周期严格解耦（Decoupled Lifecycle & Connectivity）**：
   - 监控器关闭、系统重启、SSH 断网**绝不改变远端训练的物理运行状态**。架构设计保证监控退出不影响远端；但在断线期间，客户端无法观测远端实时存活情况。
   - 断线时，界面严格只显示“连接中断；上次于 [时间] 观测为 [状态]；当前状态待重连确认”，**严禁宣称“远端仍在运行、数据未丢”**。
   - 未探测环境（如本机 WSL）必须真实显示为 `unobserved / 未观测 / 待探测`，**严禁显示为“空闲”或“已连接”**。
3. **停采不等于丢失，缺口判定基于客观不可得证据（Gap vs. Backfill）**：
   - 电脑休眠、关机、网络短暂断开属于“停采区间”。重连后若远端文件身份一致且未被截断/轮转删除，后台会自动分批补读历史，补齐后显示“已补齐”，**不插任何错误缺口横幅**。
   - 文件 mtime 变化、时间戳跳变、常规日志轮转本身**不能独立证明数据丢失**。只有已提交 offset 之后的数据因文件截断、覆盖或被物理删除导致在服务器端客观不可得时，才标记为“确认缺口 (`gap_confirmed`)”；若无法证实则标记为“可能缺段 (`gap_unknown`)”，注明原因，不捏造起止时间。
4. **收紧只读安全边界，白名单证据审查（Strict Whitelist Evidence）**：
   - 证据侧抽屉严格限制为登记任务白名单字段（PID、工作子进程、工作目录、入口脚本、启动时刻、存活时刻、队列锁状态、原始状态 JSON 镜像）。
   - **完全去除全部环境变量读取**，**完全去除系统日志（syslog/dmesg）采样**，坚决杜绝凭据泄漏或跨用户侵入。
   - 状态判定不要求 cwd、入口和 lock 全部同时满足（例如 Score 队列进程 cwd 为 `/home/cy`，但真实入口在 Score 个人目录且状态文件新鲜，仍可识别）；必须严格区分“lock 文件存在”与“进程实际持有文件锁”。Traceback 出现或日志暂时无输出不能单独等同于任务失败或死锁卡死。
5. **高信息密度与反营销模板化（Anti-Slop & High Density）**：
   - 拒绝营销落地页的宽大留白、英雄区（Hero Section）、装饰性渐变、手绘插画与纯色卡片堆叠。保留密集数据网格、等宽表格数字、双轨进度条与全功能日志流视窗。
6. **零控制只读安全底线**：
   - 界面严格不设置“启动”、“暂停训练”、“终止”、“重启”、“清理显存”等任何控制指令按钮，避免任何误触带来灾难性训练破坏。
   - 所有交互仅限于：视图切换、筛选、搜索、复制路径/元数据、暂停日志自动滚动（仅影响本地视窗）、刷新探针。

### 推荐布局 A 的核心优势
1. **盯盘专注度更高**：深度学习工程师在大部分时间内主要追踪单一活跃任务（如 Flow Matching），A 布局将右侧主工作区垂直划分为指标区与日志区，给日志流留出最大的垂直可视高度。
2. **多宿主与多阶段一览无余**：左侧树状视图能天然区分“远程服务器 lab-campus”与“本地 WSL”，并将正在训练、排队中、未启动的任务同时展示，无需在多标签间频繁切换。
3. **异常即刻感知**：未选中任务若出现状态变更（例如 Score 成功获取锁进入训练，或 lab-campus 发生连接超时），左侧列表徽标平滑闪烁提醒，保障全局态势感知。

### 4.2 进度与步数严格解耦 (累计/本轮、训练/检查点、任务状态/连接状态)

#### 4.2.1 Flow Matching 步数与进度数学模型
在断点续训场景中，tqdm 的当前迭代步数往往仅反映当前执行段，容易造成全局进度的严重误判。本设计建立严格的数学定义与解耦显示：

1. **数学前提与已知边界（Python 半开区间 `[start_step, total_steps)`）**：
   - 恢复检查点记录的零基索引：$b = \text{checkpoint}['\text{step}'] = 30000$。该检查点在历史上已完整覆盖索引 $0..b$，即累计已执行迭代次数为 $b + 1 = 30001$。
   - 本次续训段首循环执行的第一个索引：$firstLoopIndex = b + 1 = 30001$。
   - 配置目标总步数末端：$T = 200000$（为半开区间上界，不执行）。
   - 本段续训总可执行步数：$sessionTargetCount = T - firstLoopIndex = 200000 - 30001 = 169999$。
2. **tqdm 观测值与进度字段换算规则**：
   - 设 $n$ 经核验为 tqdm 解析出的已完成迭代数（例如当前观测值 $n = 80106$）：
     - **本段续训实际完成次数**：$sessionCompletedCount = n = 80106$。
       - 本段进度完成百分比：$sessionCompletedCount / sessionTargetCount = 80106 / 169999 \approx 47.12\%$。
     - **训练观测最后执行索引 (`lastStepIndex`)**：
       - 当 $n > 0$ 时：$lastStepIndex = firstLoopIndex + n - 1 = b + n = 30000 + 80106 = 110106$。
       - 当 $n = 0$ 时：$lastStepIndex = \text{null}$（本段尚未执行任何 step，不能声称已执行索引 30001）。
     - **算法全局累计完成次数 (`completedCount`)**：
       - $completedCount = (b + 1) + n = 30001 + 80106 = 110107$。
       - 全局进度完成百分比：$completedCount / T = 110107 / 200000 \approx 55.05\%$。
   - **严格前提约束**：上述公式仅在 checkpoint step 与 tqdm 语义经人工或代码确认后生效；**若任一语义未经验证，对应的 completedCount 与比例必须为 `null`，严禁猜测**。tqdm 完成次数绝不能直接填入 step 索引字段。

#### 4.2.2 Score 与 Reflow 进度的非套用原则
- **拒绝通用偏移公式**：Score 和 Reflow 的训练代码尚未实测验证其 step 是零基索引还是完成次数，也未验证其 tqdm 边界。
- **界面保真呈现**：
  - Score：显示“排队中 · 恢复点 Step 20,294 / 目标 Step 100,000”，不绘制进度条槽，不换算百分比。
  - Reflow：显示“就绪待命 · 恢复点 Step 4,000 / 目标 Step 50,000”，不绘制实时进度条。

#### 4.2.3 训练 Step 实测 vs 检查点落盘 Step
- **物理滞后客观呈现**：
  - 训练观测步数：实时提取自 `training.log`，当前最后执行索引为 Step 110,106。
  - 检查点落盘步数：读取自磁盘文件名，最新观察到的检查点为 `step 100,000`。
  - 界面明确标注：训练进度已超越最新检查点 10,106 步（反映正常的周期性保存延迟，非异常）。
- **检查点证据等级（严禁推断“保存成功”或“可恢复”）**：
  - 证据级别严格限制为：
    - `none`：未发现检查点文件。
    - `file_found`：磁盘检测到对应文件（路径、大小、mtime 正常）。
    - `file_stable_observed`：检测到文件生成且大小在连续观察窗口（如 3 秒）内保持静止。
    - `metadata_read`：读取了轻量元数据字典键（如读取了 step 数字）。
  - **红线**：Flow 代码采用采样后调用 `torch.save`，无显式保存成功日志。因此界面**严禁显示“保存成功（save_confirmed）”**，也**严禁显示“已验证可恢复”**（首版明确不加载大体积模型权重执行验证测试）。

### 4.3 高可靠日志控制台设计 (查看、搜索、暂停滚动、补读、缺口与更新时间)

#### 4.3.1 停采区间、补读与缺口判定的严格证据链
1. **停采不等于丢失（Inactive Window != Log Gap）**：
   - 电脑休眠、关机、桌面监控器关闭期间，采集器暂停工作，此时间段定义为“停采区间”。
   - 重新打开监控器时，后台发起断点续读（Catch-up）：从本地 SQLite 记录的已提交字节 offset 开始向远端请求数据。
   - 若服务器文件身份（inode/设备号）一致且大小大于等于 offset，分批补读历史字节。
   - **当积压数据全部拉取完毕且字节完全连续时，界面提示“补读完成，已补齐”，绝不出现任何红黄色的日志缺口（Log Gap）横幅**。
2. **缺口（Log Gap）的判定门槛**：
   - 仅发生文件 mtime 变更、日志文本中时间戳跳变、或者标准日志轮转（如 `training.log` 轮转为 `training.log.1` 且旧文件依然存在可读），**均不得判定为日志丢失**。
   - **确认缺口 (`gap_confirmed`)**：只有当本地游标证明已读至 offset A，而该文件被 `truncate`、内容被完全重写，或旧文件已被物理删除，导致 offset A 之后的数据在服务器端**客观不可得**时，才在日志流中插入醒目的确认缺口横幅。
   - **可能缺段 (`gap_unknown`)**：若文件身份改变且无法证明旧数据去向，标记为“可能缺段”，注明原因，**绝不凭空编造缺口的起止时间戳**。

#### 4.3.2 原始日志保真度与时间戳呈现
- **原始行原样呈现**：Flow Matching 等框架采用 tqdm 库输出进度，原始文本形如 `47%|...| 80106/169999 [3:34:14<3:56:30, 6.33it/s]`，**原始日志本身没有任何时间戳**。
- **严禁捏造日志时间戳**：界面绝不在原始日志行开头伪造 `[2026-10-18 20:31:05]` 之类的时间戳。
- **独立采集时间列**：在日志视窗中设立独立的“本地采集时间 (`ingestedAt`)”列，标明该行是监控器客户端接收并写入本地数据库的时刻，与日志原始文本彻底分离。

#### 4.3.3 自动滚动防跳锁与阅读体验 (Scroll-Lock Banner)
- **智能防跳锁机制**：
  - 当视窗处于最底部时，默认开启“自动吸底滚动 (`Auto-scroll pinned`)”。
  - 当用户使用鼠标滚轮向上回滚、或使用键盘选中文本时，自动滚动**立即平滑锁定**，界面底部悬浮微弱提示条：“自动滚动已锁定 (按空格键或点击恢复)”。
  - 锁定期间，后台新接收的日志继续静默追加到缓冲区，绝对不会粗暴将用户视窗强行拉到底部。
- **快捷键安全隔离**：
  - 空格键（`Space`）恢复滚动的快捷键**仅在日志控制台区域获得焦点时生效**，当焦点在搜索框、文本输入框或正在使用输入法（IME）时，坚决不拦截空格键输入。

#### 4.3.4 前端内存三重边界防护
为了杜绝日志流长期运行导致桌面端内存泄漏，前端虚拟滚动缓冲区设置三重硬限制：
1. **最大行数限制**：上限设定为 **10,000 行**（先进先出淘汰最旧可视行）。
2. **总字节数限制**：缓冲区内存总占用上限设定为 **8.0 MiB**（超过后即使行数未达上限也触发淘汰）。
3. **单行大小硬截断**：单行文本上限设定为 **64 KiB**。对于超长异常输出（如意外打印的完整 base64 字符串或巨型张量），自动进行尾部截断并标注 `[...行过长已截断 64KB]`，防止渲染树崩溃。

### 4.4 重启恢复与异常韧性状态治理 (重启全时序、离线、加载中、证据不足、空任务与错误状态)

#### 4.4.1 电脑重启/应用重开后的四阶段自愈时序
当运行监控器的 Windows 电脑重启或监控进程重新打开时，遵循严格的四阶段时序平滑自愈：

```
[阶段 1: 本地就绪] ──> [阶段 2: 宿主握手] ──> [阶段 3: 证据核验] ──> [阶段 4: 日志追赶]
本地 SQLite 加载       复用 SSH 别名          重新匹配进程实例        以 1MB 为批次分批拉取
展示上次已知缓存       探测宿主连通性         区分 PID 与 startTicks  更新进度并恢复实时流
(界面呈现骨架屏)       (标记为 stale)         (更新 freshness 为 fresh)(补读完成标注已补齐)
```

1. **阶段 1：本地冷启动与缓存秒开**：
   - 立即读取本地 SQLite 数据库，还原上次关闭前的任务列表与最新快照。
   - 所有任务状态标记为 `freshness: 'stale'`，明确提示“正在恢复连接，显示历史快照”。
2. **阶段 2：宿主探针握手**：
   - 复用现有 SSH 别名 `lab-campus`，发起非阻塞连通性检查（超时设为 5 秒）。
   - 若连接失败，保持 `disconnected` 状态，保留历史快照，不推测远端退出。
3. **阶段 3：进程实例与状态重新核验**：
   - 连接建立后，调用只读探针重新获取进程表。
   - 采用 `(hostBootId, pid, startTicks)` 三元组核验进程身份，防止 PID 复用导致的误判。
   - 核验通过后，将任务的 `freshness` 更新为 `fresh`，更新 `statusObservedAt`。
4. **阶段 4：日志分批有界追赶**：
   - 获取远端日志文件的当前大小，对比本地已持久化的 `endOffset`。
   - 若有积压，按每批至多 1.0 MiB 分批拉取，避免长时间占用 SSH 通道或突发磁盘 I/O。
   - 单次启动补读总量设定上限建议（如 64 MiB），超限暂停并提示待读字节，保障前台交互流畅。

#### 4.4.2 异常与边缘状态全景设计
| 异常状态 | 触发条件 | 界面呈现与状态徽标 | 用户交互与排查指引 |
| :--- | :--- | :--- | :--- |
| **断线 / 离线 (`disconnected`)** | SSH 网络超时、连接被拒、认证受阻。 | 顶栏灰黄指示 `[⊘ lab-campus 连接中断]`；任务状态显示 `[⊘ 训练中 (stale)]`，显式文字：“连接中断；上次于 20:31:05 观测为训练中；当前状态待重连确认”。**不宣称远端存活或数据未丢**。 | 提供“立即重试”按钮；显示下次自动重试倒计时。 |
| **骨架加载中 (`loading`)** | 初次启动、正在探测握手。 | 骨架屏（Skeleton Loading），所有指标卡维持最终尺寸微弱呼吸，避免布局抖动（CLS < 0.1）。 | 无需操作，后台自动进行。 |
| **待确认 (`unconfirmed`)** | 进程退出无退出码；或个人目录匹配但缺少关键入口信息；或证据冲突。 | 黄色问号徽标 `[? 待确认 UNCONFIRMED]`；主控制台弹出证据链审查卡，逐项列出已确认与缺失项。 | 点击查看证据详情抽屉，展示白名单字段排查诊断建议。 |
| **空任务状态 (`not_observed`)** | **仅当宿主已连接且完整执行登记范围探测后**，未发现匹配的任务活动。 | 中性提示卡片：“本轮已连接且登记目录探测完整，未发现登记训练任务”。**未观测的 WSL 严禁使用此状态**。 | 检查登记路径配置，或在宿主启动训练后自动捕获。 |
| **采集受阻 (`source_missing` / `permission_error`)** | 目标日志读取权限不足（EACCES）、文件被意外删除。 | 局部错误标签 `[⚠ 无法读取 training.log: 权限受限]`；明确显示 Linux 错误码与路径，**隔离故障，不影响其他任务**。 | 复制路径，提示用户在服务器核对文件读权限。 |
| **排队等待中 (`queued`)** | 检出队列进程，持锁确认且状态文件为 `waiting_flow`。 | 琥珀色沙漏徽标 `[⏳ 排队中 QUEUED]`；主面板展示队列依赖：“正在等待 Flow Matching 释放资源”，展示持锁时长与队列日志。 | 点击查看前置依赖任务，查阅 queue.log。 |

#### 4.4.3 状态判定的审慎原则
- **Traceback 出现不等于任务失败**：Python 训练中可能出现预料内的捕获异常、重试日志或 DataLoader 临时警告，不能仅凭抓取到 `Traceback` 关键字就将生命周期改为 `failed`。必须结合进程是否真实退出（非零 exit code）综合判定。
- **日志静默不等于死锁卡死**：模型在进行大批量验证集评测（Evaluation）、生成高分辨率采样图片、或正在落盘大体积检查点时，可能出现数分钟的日志静默，不能轻率判为 `stalled`。只有超过预设阈值且 GPU 利用率持续为 0 时，才标为 `stalled_suspected`（疑似停滞）。

### 4.5 排版、易用性、无障碍与空间适配 (中文/数字、状态编码、白名单证据、全键盘、长路径与小窗口)

#### 4.5.1 中文排版与等宽表格数字准则
- **字体栈配置**：
  - **界面通用文字 (UI Text)**：`"Segoe UI Variable Text", "Microsoft YaHei UI", -apple-system, sans-serif`。字重控制在 Regular (400) 与 Medium (500)，避免中文字体粗暴加粗导致的像素糊化。
  - **数值与代码 (Monospace & Numbers)**：`"Cascadia Code", "Consolas", "JetBrains Mono", monospace`。
- **等宽表格数字（Tabular Numbers）**：
  - 所有数值（Step、完成次数、显存大小、速率、百分比、时间戳）强制启用 CSS 属性：
    `font-variant-numeric: tabular-nums; font-feature-settings: "tnum";`
  - 保证数值在动态刷新递增时，字符宽度恒定，数字列绝不发生左右抖动。
  - 千位分隔符：大于 999 的所有计数值均使用逗号分隔，如 `110,107 / 200,000`。
- **行高与防换行**：
  - 正文采用 `leading-normal (1.5)`，关键状态徽标与数值单位设置 `white-space: nowrap` 严格禁止非预期折行。

#### 4.5.2 状态的多重编码（超越色彩的辨识保障）
严禁“仅靠红绿颜色”传达状态。所有状态统一采用**“特征符号 + 边框形状 + 显式文字 + 功能色”**四重编码，确保色盲群体或远距离副屏均能秒级识别：

| 状态 | 符号 | 边框/容器形状 | 显式文本 | 建议色彩 (深色底) | 建议色彩 (浅色底) | 辨识保障 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **运行中 (running)** | `●` | 实心胶囊丸 (Pill) | `运行中 RUNNING` | 祖母绿 `#10B981` | 墨绿 `#059669` | 实心圆 + 完整文字 |
| **排队中 (queued)** | `⏳` | 圆角矩形 (Rounded) | `排队中 QUEUED` | 琥珀金 `#F59E0B` | 赭黄 `#D97706` | 沙漏符号 + 独立矩形 |
| **就绪未启动 (ready)** | `○` | 虚线外框圆角 | `就绪 READY` | 冰板岩蓝 `#94A3B8` | 钢灰 `#64748B` | 空心圈 + 虚线外框 |
| **未观测 (unobserved)** | `○` | 点状边框圆角 | `待探测 UNOBSERVED`| 沉淀灰 `#64748B` | 浅灰 `#9CA3AF` | 空心小圈 + 灰度弱化 |
| **连接中断 (disconnected)**| `⊘` | 倾斜线框标 | `断开 DISCONNECTED`| 烟灰红 `#EF4444` | 暗红 `#DC2626` | 禁止斜线标 + 警示字 |
| **异常受阻 (error)** | `▲` | 尖角警告三角 | `异常 ERROR` | 绯红 `#F43F5E` | 鲜红 `#E11D48` | 三角警告符 + 高对比 |
| **待确认 (unconfirmed)** | `?` | 问号方框 | `待确认 UNCONFIRMED`| 硫磺黄 `#EAB308` | 褐黄 `#CA8A04` | 问号几何 + 独立方框 |

#### 4.5.3 白名单证据侧抽屉 (Evidence Drawer)
点击“证据详情”滑出只读审查抽屉，**仅呈现已登记任务的白名单字段**：
1. `mainPid`：主进程 PID (如 `594319`)。
2. `workerPids`：工作子进程列表 (如 `[594320, 594321, 594322, 594323]`)。
3. `cwd`：当前工作目录 (如 `/data2/cy/xzn/Code/Flow_Matching`)。
4. `scriptEntry`：真实脚本入口 (如 `torchcfm/examples/images/cifar10/train.py`)。
5. `startedAt`：进程启动时刻 (从系统时钟域读取)。
6. `lastObservedAlive`：最后一次确认存活时刻。
7. `queueLockStatus`：队列锁状态（分项展示：`lockFileExists: true`, `lockHeldByProcess: true`）。
8. `statusJsonRaw`：状态文件原始 JSON 镜像（限长脱敏展示）。
- **隐私与权限红线**：**完全去除任何环境变量（如 PATH、CUDA_VISIBLE_DEVICES、TOKEN 等）**，**完全去除系统日志（syslog/dmesg）展示**。

#### 4.5.4 长路径智能省略与单触复制
服务器路径通常极长（例如 `/data2/cy/xzn/Code/Flow_Matching/torchcfm/examples/images/cifar10/results_server_resume/training.log`）。
- **显示策略**：采用**中间省略（Middle Ellipsis）**，保留根目录与尾部文件名：`/data2/cy/xzn/.../results_server_resume/training.log`。
- **单触复制**：路径后附带复制图标 `[📋]`，点击瞬间变为 `[✓ 已复制]`，将规范化的服务器绝对路径复制到 Windows 剪贴板。

#### 4.5.5 全键盘操作与无障碍设计 (Keyboard & a11y)
- **快捷键作用域隔离**：
  - `Ctrl + 1 ~ 3`：切换左侧任务焦点（全局有效）。
  - `Ctrl + F`：焦点快速射入日志搜索框。
  - `Space`（空格键）：暂停/恢复日志自动滚动（**仅在日志窗口具有焦点时生效，严禁在搜索框或输入法激活时拦截**）。
  - `Esc`：清空日志搜索词，或关闭证据抽屉。
  - `Ctrl + R`：触发一次即时宿主与日志探针，重置轮询计时器。
- **屏幕阅读器防轰炸**：
  - 日志流视窗采用 `role="log"`，设置 `aria-live="polite"`；**严禁对高频追加的日志行设置逐行强制朗读**，仅在出现严重错误或连接断开等重大状态改变时触发语音播报。

#### 4.5.6 小窗口自适应机制 (960 × 600 响应式收折)
- **基准与极限**：基准尺寸为 `1280 × 800`，允许缩小的最小尺寸为 `960 × 600`。
- **紧凑降级规则**：
  1. **左侧任务栏收折为紧凑导轨或顶栏下拉框**：在极小宽度下，任务切换转为顶部的 `[当前任务: Flow Matching ▼]` 下拉菜单。
  2. **双轨进度条紧凑排列**：累计与本段进度条上下间距压缩，指标卡从三列栅格收缩为两列。
  3. **日志工具条自适应**：搜索框默认收缩，获得焦点时平滑展开。

## 6. 前端所需数据契约草案 (Data Contract)

为保证前端展示层与数据采集层严格对齐，本契约完全采纳 `docs/drafts/data-design.md`（Luna 草案修订版）的数据语义。数据字段充分支持 `unknown`、`null`、新鲜度标记与资源范围隔离：

```typescript
/** 宿主物理连接状态 */
export type Connection = 
  | 'connected'            // 物理连接正常且最近一次探测成功
  | 'connecting'           // 正在建立连接或执行握手探针
  | 'disconnected'         // 网络断开、超时或主机不可达
  | 'permission_error'     // 登录或访问权限受阻
  | 'source_missing'       // 目标文件或环境不存在
  | 'unknown';             // 尚未发起探测 (如初始状态的 WSL)

/** 任务生命周期状态 */
export type Lifecycle = 
  | 'running'              // 确认检出匹配的训练进程且活跃推进
  | 'queued'               // 任务状态文件/队列日志明确等待，训练尚未开始
  | 'ready_not_training'   // 状态文件明确就绪，无开始训练证据
  | 'completed'            // 目标达成且有正常退出证据
  | 'failed'               // 有明确退出报错或崩溃证据
  | 'stalled_suspected'    // 进程存在但超期无任何进度推进 (仅疑似)
  | 'unconfirmed'          // 证据冲突或不足，无法归属
  | 'not_observed'         // 本轮探测完整，未发现登记任务
  | 'unknown';             // 从未成功观测

/** 证据可信度等级 */
export type Confidence = 'high' | 'medium' | 'low' | 'none';

/** 宿主快照模型 */
export interface HostSnapshot {
  hostId: string;                     // "lab-campus" | "wsl-ubuntu"
  kind: 'wsl' | 'ssh';
  connection: Connection;
  observedAt: string | null;          // ISO 时间戳，null 表示从未成功观测
  lastSuccessAt: string | null;       // 最后一次成功连通时间戳
  errorCode?: string;                 // 脱敏诊断码，严禁包含凭据
}

/** 证据条目 */
export interface Evidence {
  kind: string;                       // "process_match" | "status_json" | "queue_lock"
  source: string;                     // 证据来源路径或探针指令
  observedAt: string;
  confidence: Confidence;
  summary: string;                    // "检测到 PID 594319 且真实入口吻合"
}

/** 进程实例键与信息 (三元组防 PID 复用) */
export interface ProcessInstance {
  hostBootId: string | null;          // 主机启动标识
  pid: number;
  startTicks: string | null;          // 进程启动时钟 ticks
  parentPid: number | null;
  cwd: string | null;                 // "/data2/cy/xzn/Code/Flow_Matching"
  scriptEntry: string | null;         // "torchcfm/examples/images/cifar10/train.py"
  role: 'trainer' | 'queue' | 'worker' | 'unknown';
}

/** 资源快照指标 (明确 scope 与 deviceId，严禁把整卡占用冒充本进程) */
export type ResourceMetric = {
  observedAt: string;
  name: 'gpu_utilization' | 'gpu_memory_used' | 'gpu_memory_total' | 'cpu_utilization' | 'process_rss';
  unit: '%' | 'bytes';
  value: number | null;               // 无法采集时为 null
} & (
  | { scope: 'device'; deviceId: string; processKey: null }
  | { scope: 'process'; deviceId: string | null; processKey: { hostBootId: string; pid: number; startTicks: string } }
);

/** 任务完整快照模型 */
export interface TaskSnapshot {
  taskId: string;                     // "flow_matching" | "score_based" | "reflow"
  hostId: string;                     // "lab-campus"
  lifecycle: Lifecycle;
  
  // 新鲜度与状态观测时刻 (断网时保留最后状态并标记为 stale)
  freshness: 'fresh' | 'stale' | 'unobserved';
  statusObservedAt: string | null;
  confidence: Confidence;
  reason: string;                     // 状态判定依据简述
  evidence: Evidence[];               // 白名单证据链

  // 进程归属 (主进程、队列角色及工作子进程)
  processes: {
    main: ProcessInstance | null;
    queue: ProcessInstance | null;
    workers: ProcessInstance[];       // DataLoader 等子进程
  };

  // 进度严格解耦模型
  progress: {
    lastStepIndex: number | null;     // 训练实测最后执行索引 (n=0 时为 null)
    resumeCheckpointIndex: number | null; // 恢复检查点记录索引 (如 30000)
    firstLoopIndex: number | null;    // 本段首循环索引 (如 30001)
    
    // 算法全局累计视角
    global: {
      completedCount: number | null;  // 累计完成总次数 (如 110107)
      targetCount: number | null;     // 算法总目标次数 (如 200000)
      fraction: number | null;        // completedCount / targetCount (如 0.5505)
      unit: 'completed_iterations' | 'unknown';
      source: string;
      verified: boolean;              // 算法语义是否已核实
    };

    // 本段续训执行视角
    session: {
      completedCount: number | null;  // 本段完成迭代数 (如 80106)
      targetCount: number | null;     // 本段目标总数 (如 169999)
      fraction: number | null;        // 如 0.4712
      unit: 'completed_iterations' | 'unknown';
      source: string;
      verified: boolean;
    };
  };

  // 检查点落盘状态
  checkpoint: {
    path: string | null;              // 检查点文件相对或绝对路径
    fileStepIndex: number | null;     // 文件名标记的 step (如 100000)
    sizeBytes: number | null;         // 文件大小
    observedAt: string | null;
    evidence: 'none' | 'file_found' | 'file_stable_observed' | 'metadata_read'; // 绝不虚构 save_confirmed
  };

  // 资源观测列表
  resources: ResourceMetric[];
}

/** 增量日志事件模型 (支持补读进度与客观缺口) */
export interface LogEvent {
  taskId: string;
  sourceId: string;                   // 日志源标识: "training_log" | "queue_log"
  generation: string;                 // 文件代次标识 (轮转/截断时更新)
  kind: 'line' | 'gap_confirmed' | 'gap_unknown' | 'catchup' | 'cache_evicted';
  startOffset: number;                // 原始文件起始字节偏移
  endOffset: number;                  // 原始文件结束字节偏移
  ingestedAt: string;                 // 本地采集入库时间 (ISO 8601)
  
  // 补读追赶进度 (总量未知时 bytesTotal 为 null)
  catchupBytesRead: number | null;
  catchupBytesTotal: number | null;

  text?: string;                      // 原始日志行文本 (不附加伪造时间戳)
  reason?: string;                    // gap 或 cache_evicted 的原因说明
}
```

## 7. 建议的视觉方向与技术栈选型理由

### 7.1 建议的视觉风格方向：冷色工程控制台 vs 现代明亮控制台
> **注：主题偏好目前尚未定稿，以下提供暗色与浅色两套高品质方案，供用户根据使用场景最终决策。**

#### 方案 A：冷色工程控制台 (Cold Precision Console - 暗色方案)
- **基调**：针对长周期挂屏（副屏持续监控数天）设计，底色采用深度冷墨黑与深板岩蓝（`#0B0F17`），卡片采用 `#131B2A`，边框采用 `#222F44`。
- **色彩语义**：
  - 基础文本：主要文字冷白 `#F8FAFC`，次级说明 `#94A3B8`。
  - 唯一运行色：祖母绿 `#10B981`（专用于 running 状态与步数递增）。
  - 唯一排队色：琥珀金 `#F59E0B`（专用于 queued 状态与补读进度）。
  - 唯一警告色：绯红 `#EF4444`（专用于连接中断与确认缺口）。
- **优势**：弱光环境下对比温和，无刺眼白底；严格杜绝 AI 赛博紫/荧光杂色。

#### 方案 B：现代工程控制台 (Clean Precision Console - 浅色方案)
- **基调**：适合日间明亮采光办公室，底色采用纯净冷灰白（`#F8FAFC`），卡片采用纯白底（`#FFFFFF`），边框采用细致冷灰（`#E2E8F0`）。
- **色彩语义**：
  - 基础文本：主要文字深灰 `#0F172A`，次级说明 `#64748B`。
  - 运行色：深墨绿 `#059669`；排队色：深赭黄 `#D97706`；警告色：深艳红 `#DC2626`。
- **优势**：文字边缘清晰锐利，明室阅读对比度极高，符合经典 IDE 浅色工程模式。

### 7.3 采集与轮询工程预算建议 (待测目标，非绝对承诺)
- **轮询周期**：活跃宿主建议 **每 15 秒** 轮询一次进程与状态元数据；单次命令超时设定为 5 秒，最多重试 1 次。坚决拒绝 10Hz 等高频轮询需求，防止对远程服务器与 SSH 造成负载干扰。
- **补读吞吐预算**：每个日志源每轮至多拉取 256 KiB；断线/重启补读时每批至多 1.0 MiB，批间让出轮询机会；单次启动补读总量上限建议先设为 64 MiB。
- **节流与只读保护**：所有远端访问严格走只读通道，虽然极度轻量，但也必须实施主动节流，**不能虚构绝对零 I/O 影响**。

---

### 7.4 本地 7 天缓存与淘汰机制
- **留存基准**：严格以本应用本地入库时间 `ingestedAt` 作为 7 天 TTL 的淘汰依据，**绝不使用日志文本中的时间戳或远端文件 mtime**。
- **容量上限建议**：本地数据库建议总上限设定为 **1.0 GiB**，单一任务日志上限设定为 **256 MiB**。
- **淘汰策略**：达到上限时，自动淘汰最旧入库数据至 80% 水位，并在日志流中记录 `cache_evicted` 事件。
- **安全红线**：只删除监控器本机的本地缓存文件，**绝对不触碰、不修改、不删除远端服务器的任何原始日志、检查点或代码文件**。

## 8. 实施准备与交付说明

### 8.1 本轮修订解决的核心核对项清单
对照 `docs/reviews/design-alignment.md` 主控核对表，本稿已完成以下实质性修订：

1. **断线状态真实性**：全面消除“远端仍运行、数据未丢”的断言，统一修改为“连接中断；上次于 [时间] 观测为 [状态]；当前状态待重连确认”；WSL 初始状态纠正为 `unobserved / 待探测`，不再标为空闲或已连接。
2. **步数与进度边界严谨化**：严格区分零基 step 索引、完成次数、本段完成次数与目标边界；明确 Flow 半开区间数学公式及其成立前提；Score 和 Reflow 仅展示恢复基线点与目标，实时进度标为 `null`；检查点仅保留 `file_found` 与 `metadata_read` 真实等级，杜绝“保存成功”或“可恢复”的虚构。
3. **日志缺口与补读客观化**：明确停采区间不等于丢失；补读完整则标为“已补齐”，不插入缺口横幅；缺口仅在数据物理不可得时呈现；原始 tqdm 日志无时间戳如实保留，本地采集时间单列。
4. **证据抽屉白名单化**：彻底移除环境变量与 syslog/dmesg 读取，收紧为白名单进程与文件字段；明确 lock 文件存在不等于持锁；Traceback 或日志静默不轻率等同于任务失败或卡死。
5. **数据契约对齐**：契约全面引入 `unknown`、`null`、`freshness`、`statusObservedAt`、`ProcessInstance` 进程三元组、区分设备级与进程级的 `ResourceMetric`、包含 `generation` 与 `offsets` 的 `LogEvent`，完全兼容 Luna 的数据草案。
6. **性能表述去绝对化**：内存控制同时约束行数（10,000行）、字节（8.0 MiB）与单行大小（64 KiB）；删除未实测的常驻内存、零显存及零 I/O 承诺；刷新与读取预算作为工程待测目标，明确拒绝 10Hz 高频轮询。
7. **数据模拟标注与无障碍优化**：所有示例数值与日志行显式标注为 `[模拟数据]`；快捷键（如空格键）严格限定在日志控制台内，不干扰输入法与搜索框；主题偏好保持客观中立，留待用户决定。
