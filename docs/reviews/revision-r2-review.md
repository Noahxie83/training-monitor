## 原审查六个场景复演

以下均为按 r2 文字规则进行的桌面推演，不是实测。

1. **Flow 单源超时、Score 状态可读：通过。** Flow 请求的超时仅令该源失败并退避；无传输阶段证据时触发独立宿主探测。探测成功则宿主在线，Score/身份状态到期任务优先，不继承 Flow 的 retryAt（§6.4）。
2. **首次导入起点落在行中间：通过。** 以固定 S 开始，首条保存 S 至 LF（包含分隔字节，示例为 `[S,S+201)`），标记 prefixIncomplete；后续从 S+201 开始。所有原始字节在事务成功前不推进 C，完成后 C=E；重开从 C 继续，不重复提交（§6.1–6.2）。
3. **同 inode 从旧 C=8MiB 截断并长至10MiB：通过。** 锚点不匹配进入 reconciling，禁止以旧 C 读取新内容。旧归档可验证时从旧代次续读；否则按旧 H 与可得性证据决定可证明的 gap 或 unknown，并原子创建新代次从0读。不会把新文件 8–10MiB冒充旧区间（§6.2）。
4. **PID 数字复用且主机重启：通过。** hostBootId 改变导致 runId 改变；当前 run 不继承缓存 n、索引或旧基线。不能关联到新 run 的日志保留展示但不更新进度；相关 Progress 字段 null（§4.4）。
5. **Score cwd=/home/cy 且没有 queue.lock：通过。** 真实入口、已确认队列实例和匹配等待记录足以识别 queued；锁不是必要条件，持锁可为 null。打开 fd 不作为持锁证据（§4.3、§8）。
6. **宿主在线、训练日志暂缺且状态 waiting：通过。** 源可报 missing 并按30秒重查；宿主/其他源状态独立，任务不因日志尚未生成而转 failed（§5.1、§6.4）。

## 非阻塞建议

- §6.2 明确有限锚点可能漏掉恰好保留所有采样字节的快速同 inode 覆盖；此限制已写明且要求有疑义时 reconcile，属于可接受的证据边界。实施计划应保留“锚点不能证明全文件连续”的限制，不把锚点匹配宣传为绝对完整性保证。
- §4.4 的直接写入证据仅证明该进程打开可写 fd 并在观察窗口内有新增完整输出；fd 不排他，不能证明没有共同写入者。r2 已明确不声称排除所有共同写者，发现混写/矛盾即撤销绑定并待确认。实现应继续对无归属输入保持 `runId/bindingId=null`，不可用路径或计数猜归属。
- §4.4、§5.2 与 §8 对无法归属进度的处理一致：Progress 的 runId、基线、索引、global/session 计数、比例、速率、ETA 按条件置 null；配置目标可单列，原始日志保留。建议计划中的解析器接口维持字段级 null，避免将整个任务状态误降为零或用 null 覆盖可独立显示的原始索引。
- Electron、主题、轮询/缓存预算及其他 §2 默认提案仍是完整设计中的待确认方案；r2 明确此边界。实施计划可标明其决策状态，不应写作用户已批准。

## 无法验证的事实

本审查不能验证真实服务器/WSL 的文件系统行为、轮转候选和权限、锚点碰撞概率、fd 写入观察能力、SSH/WSL/Python/nvidia-smi 可用性、性能/资源开销，或真实算法的运行与计数语义。尤其“旧归档是否完整可读”“完整检查候选后某字节是否客观不可得”取决于部署时允许检查的具体来源；r2 对候选范围和证据门槛有规则，但事实只能在后续获授权的只读预检/实测中确认。文档桌面推演不替代这些验证。
