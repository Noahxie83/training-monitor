## 四项原阻塞复核

| 原问题 | 状态 | r2 章节依据与独立判断 |
| --- | --- | --- |
| 1. 单源失败与宿主级退避混淆 | **已闭合** | §6.4 第 215—223 行明确区分 host/source：传输、握手、认证拒绝和明确断连为 host；宿主已应答后的单文件 missing/permission/read/protocol 为 source。源 retryAt 不被其他源或宿主元数据继承。无阶段证据的 timeout 先失败当前请求、使宿主按时间 stale，再执行独立有界宿主探测；探测成功只让失败源退避，探测失败才置宿主 disconnected。每宿主一个 in-flight 时，到期身份/状态/资源优先于日志重试和补读，不能连续派发日志重试。 |
| 2. 首次导入、行边界与 offset 语义 | **已闭合** | §6.1 第 156—160 行统一半开 `[start,end)`，首次固定 EOF=E、S=max(0,E-5MiB)、G=C=S、H=E，再完整保存 `[S,E)`；不再向 S 前寻找行首，首条可标 `prefixIncomplete`。§6.2 第 168—174 行明确 C 是 `[G,C)` 原字节曾连续成功入库的位置，不是行尾；CRLF、UTF-8 carry、超长未完成行和解析状态与 C 同事务。第 172 行规定 CAS 检查 generation/revision/C；迟到或部分重叠响应不得插入，完全已提交响应丢弃，部分重叠从当前 C 重取。§8 第 243 行再次统一半开区间。 |
| 3. 同 inode copytruncate 与代次转换 | **已闭合** | §6.2 第 181—191 行规定身份、size<C、锚点失配或弱身份不确定时进入持久化 `reconciling`，保留旧 C/H/carry，禁止从旧 C 接受可疑当前文件；允许从登记的旧归档按身份/内容锚点补读旧代次。旧代次封存、缺口决定、新 generation UUID、G=C=0、新 H 和清空新解析状态在同一事务完成；新文件从 0 分批读取，不套首次 5 MiB、不继承旧 C。`gap_confirmed` 同时要求旧未提交 `[C,H)` 与完整候选检查后确认不可得；H=C 或检查不足只能 `gap_unknown`。 |
| 4. runId 生成与旧进度嫁接 | **已闭合** | §4.4 第 89 行以 `[hostId,taskId,hostBootId,pid,startTicks]` 的规范 JSON 计算 SHA-256；只有确认的主训练实例生成，queue/workers 不生成。bootId 或 startTicks 变化即新 run。第 91—95 行以 RunBinding 的 `[fromOffset,throughOffset)` 和两类有限证据关联日志，观察窗口从当时 EOF 开始，断线/重开/身份变化/连续性破坏关闭窗口。第 97—99 行明确新 run 或身份不明时清空当前进度，同强键重开只显示 stale 旧绑定，停采新增字节不自动刷新；全局派生值还要求同 run 基线。第 8 节把日志 generation 与训练 run 分开，新 generation 不继承旧绑定。 |

## 补充矛盾探测

| 场景 | 推演结果 |
| --- | --- |
| 迟到响应从旧 C 开始并跨过当前 C | 响应起点不等于当前 C，CAS 失败；完全已提交部分丢弃，部分重叠整段作废并从当前 C 重取，不会重复展示或把重叠字节接到错误的解析状态。依据 §6.2 第 172 行。 |
| 同一强键 run 在监控关闭期间继续训练，重开后从当前 EOF 建新窗口 | runId 可保持相同，但旧进度只能以 stale 显示；停采期间未绑定字节不追认为该 run，新窗口后的完整绑定记录才可刷新进度。依据 §4.4 第 95、97 行。 |
| copytruncate 转换事务中途崩溃 | 事务提交前恢复旧代次游标；提交后恢复新 generation 的 C=0 或已提交 C，不会混合新旧解析状态。依据 §6.2 第 184、187 行。 |
| 续训进程直接写日志且 tqdm 只用 CR 重绘 | §6.2 第 174 行支持单独 CR 重绘和持久化 pendingCR，原始 offset 不按显示行推进；绑定规则要求“完整记录”，实现计划应明确已完成的 CR 重绘也算完整记录，否则可能漏掉 tqdm 进度绑定。该项属于接口澄清建议，不构成本轮阻塞。 |
| 检测到日志混写后撤销 RunBinding | §4.4 第 93 行要求撤销该段归属并置待确认，能防止继续嫁接；第 8 节 RunBinding 尚无 valid/revokedAt 等内部字段，实施计划需定义撤销或删除后的进度重算方式。该项不改变 r2 的“不得嫁接”结论，属于内部契约细化建议。 |

## 一般建议

- 在 §4.4 的“新 run 清空当前进度”中，实施计划应明确 `bindingIds=[]`、`baselineEvidenceId=null`，避免只清 runId/数值而保留旧绑定引用。
- 在 §6.2 的代次切换中，建议把“当前文件可读且稳定”限定为身份、锚点和读取前后一致性稳定，允许正常追加改变 size/mtime；否则可能被误解为必须等文件停止增长才能换 generation。
- 建议明确 §4.4 的二类证据中“完整记录”包含已经由 CR 终结的 tqdm 重绘记录，而不只包含 LF/CRLF 行。
- 建议明确 RunBinding 撤销的内部状态或删除语义，并规定撤销后相关 Progress 立即重算或置 null。
- §4.4 第 91 行与第 93 行的“初次识别 run 前已有字节不追认”和“已有结构化启动记录可绑定”之间，建议在实施计划中明确证据①只适用于观察窗口开启后取得的记录，避免把初始未关联历史重新追认。该澄清是保守化建议，不阻塞当前批准。
- §8 的 `ResourceMetric` 进程范围仍要求非空 `ProcessKey`；若句柄可用但启动标识缺失，实施计划应直接省略该指标或降级为设备能力缺失，不构造弱实例键。该点与 r1 阻塞无关，仅建议在计划中锁定。
